## Shared Platform Module

`common` is a backend library module, not a runnable service. It owns shared Quarkus plumbing that should stay identical across services:

- `X-Request-Id` propagation
- JSON API error responses
- liveness health check wiring
- geospatial validation, distance, bearing, altitude delta, and camera-oriented minimap offset math
- AR anchor confidence scoring shared by memory capture and camera HUD/minimap projections

All runnable services depend on `common` instead of copying these classes. New services should follow the same pattern and index the shared module in `application.properties` so Quarkus discovers the shared filters, exception mapper, and health check.

The social service now exposes a graph-first network projection at `GET /social/network/{userId}?maxDepth=2`, returning graph nodes and edges for direct friends, friends-of-friends, family, groups, and communities. `GET /social/neighborhood/{userId}?maxDepth=2&limit=10` summarizes the visible neighborhood into relation buckets, top connectors, joined circles, and hidden-by-block counts for discovery, minimap, feed, and future audience segmentation. `GET /social/audience/preview?ownerId=...&scope=friends&targetId=...` resolves post/photo/story audiences for private, friends, close friends, family, group, and community scopes while marking public as non-enumerable; `GET /social/audience/decision?ownerId=...&viewerId=...&scope=friends&targetId=...` returns the per-viewer enforcement decision and reason for the same scopes; `POST /social/audience/decision/batch` evaluates up to 100 viewers in one request for feed, fanout, notification, camera, and minimap enforcement; `POST /social/audience/access` evaluates one viewer against up to 100 candidate owners and returns allowed/denied owner IDs for feed and minimap filtering. Social content is managed with `POST /social/content`, `GET /social/content/{contentId}?viewerId=...`, `POST /social/content/access`, and `GET /social/feed?viewerId=...&limit=20`, which returns audience-filtered feed items with relation, visibility reason, like/comment/save/share counts, viewer-liked/saved state, and a transparent ranking score. Likes use `PUT /social/content/{contentId}/likes` plus `DELETE /social/content/{contentId}/likes/{userId}`; saves use `PUT /social/content/{contentId}/saves`, `DELETE /social/content/{contentId}/saves/{userId}`, and `GET /social/users/{userId}/saved-content`; shares use `POST /social/content/{contentId}/shares` and `GET /social/content/{contentId}/shares`; hides use `PUT /social/content/{contentId}/hides`, `DELETE /social/content/{contentId}/hides/{userId}`, and `GET /social/users/{userId}/hidden-content`; reports use `POST /social/content/{contentId}/reports` and `GET /social/content-reports?status=open&limit=50`; mentions are extracted from captions/comments as `@user_id`, filtered through audience/block rules, and exposed through `GET /social/content/{contentId}/mentions?viewerId=...` plus `GET /social/users/{userId}/mentions`; comments use `POST`, `GET`, and `DELETE` under `/social/content/{contentId}/comments`, accept optional `parentCommentId` for replies, return `replyCount`, `likeCount`, and `viewerLiked`, use `GET /social/content/{contentId}/comments?viewerId=...&parentCommentId=...` to fetch one reply thread, and support `PUT /social/content/{contentId}/comments/{commentId}/likes` plus `DELETE /social/content/{contentId}/comments/{commentId}/likes/{userId}`. Activity and notification trails are available through `GET /social/activity/{userId}?mode=inbox|outbox|all&limit=50` and `PUT /social/activity/{activityId}/read?actorUserId=...`; content creation, first likes, comment likes, shares, comments, replies, and mentions emit activity records with unread state for the recipient. Family links are managed through `PUT /social/family`, `GET /social/family/{userId}`, and `DELETE /social/family/{userId}/{relativeId}`; circles are managed through `POST /social/groups`, `PUT /social/groups/{groupId}/members`, `PUT /social/groups/{groupId}/members/{memberId}/role`, `DELETE /social/groups/{groupId}/members/{memberId}`, `POST /social/communities`, `PUT /social/communities/{communityId}/members`, `PUT /social/communities/{communityId}/members/{memberId}/role`, and `DELETE /social/communities/{communityId}/members/{memberId}`. Circle membership protects the last owner from removal or demotion. Group/community join-request queues, invite queues, user circle-request inboxes, and circle content-moderation queues accept `limit` and `cursor`, returning `hasMore` and opaque `nextCursor` hints. `GET /social/recommendations/{userId}?limit=20` ranks connection suggestions from mutual friends, shared groups, shared communities, and family links while excluding existing friends, pending requests, and blocked users. `GET /social/relationships/context?viewerId=...&ownerId=...` summarizes pairwise relationship depth, affinity score, mutual friends, shared circles, family/pending/block state, and the nested visibility decision for profile, camera, feed, and future ranking consumers; `POST /social/relationships/context/batch` accepts one viewer and up to 100 owner IDs for minimap/feed batch hydration without client-side N+1 calls. `GET /social/relationships/path?fromUserId=...&toUserId=...&maxDepth=3` returns an explainable visible path across friend, family, shared-group, and shared-community edges so clients can answer why a person appears. `SocialService` talks through a `SocialGraphRepository` boundary backed by the current in-memory implementation by default, and can switch to the Bolt-backed Neo4j repository with `jezaku.social.graph.repository=neo4j` plus `jezaku.social.neo4j.uri`, `username`, `password`, and optional `database`. Sample graph data remains enabled for memory mode, but Neo4j seed data is opt-in with `jezaku.social.seed.neo4j.enabled=true` for local smoke tests. Set `jezaku.social.neo4j.apply-schema=true` to apply the bundled constraints/indexes at startup, and call `GET /social/graph/repository` to confirm the active backend. The Neo4j baseline schema and Cypher notes live in `Backend/social/src/main/resources/neo4j/social_graph_schema.cypher`.

Content responses include an `owner` profile card, and comment responses include an `author` profile card, both hydrated with display name, handle, avatar URL, visibility, and `profileVisible` from the requesting viewer's perspective. Feed, timeline, saved-content, hashtag, topic, detail, and comment screens can therefore render attribution without issuing profile lookups per row. Ranked feeds support cursor pagination with `GET /social/feed?viewerId=...&limit=20&cursor=...` and `GET /social/users/{userId}/following-feed?limit=20&cursor=...`, returning `hasMore` and an opaque `nextCursor` while keeping `visibleCount` and `hiddenCount` for the full candidate set. Profile timelines, hashtag content, topic feeds, group timelines, community timelines, saved-content libraries, hidden-content libraries, content shares, content reports, content mentions, and user mention inboxes also accept `cursor` and return the same `hasMore`/`nextCursor` paging hints. Comment lists support cursor pagination with `GET /social/content/{contentId}/comments?viewerId=...&parentCommentId=...&limit=25&cursor=...`, returning `hasMore` and an opaque `nextCursor` per thread. Like, save, share, comment-like, and mention rows also include their relevant `user`, `actor`, or `mentionedUser` cards so action sheets and mention drawers can render people directly.

Friend graph screens can use `POST /social/friend-requests`, `GET /social/friend-requests/{userId}?direction=incoming&status=pending&limit=50&cursor=...`, `POST /social/friend-requests/{requestId}/accept`, `POST /social/friend-requests/{requestId}/decline`, `GET /social/friends/{userId}?viewerId=...`, and `GET /social/close-friends/{userId}?viewerId=...`. Friend requests, friends, close friends, followers, following, and follow-request inboxes accept `limit` and `cursor`, returning `hasMore` and opaque `nextCursor` hints for large graph lists. Friend request rows include `fromUser` and `toUser` profile cards, while friend and close-friend rows include a `friend` card with display name, handle, avatar URL, visibility, and `profileVisible` from the viewer's perspective. Recommendations from `GET /social/recommendations/{userId}?limit=20&cursor=...` include `hasMore`/`nextCursor`, the recommended user's profile card, and bounded mutual-friend, shared-group, and shared-community previews, keeping discovery screens explainable without extra per-row lookups.

Activity badges can use `GET /social/activity/{userId}/summary` for whole-inbox unread counts and type breakdowns, while `PUT /social/activity/{userId}/read-all` clears the user's unread inbox in one request. Activity lists support cursor pagination with `GET /social/activity/{userId}?mode=inbox&limit=50&cursor=...`, returning `hasMore` and an opaque `nextCursor`; `unreadCount` still reports the full matching inbox count, not just the current page. Activity rows include `actor` and `recipient` profile cards from the requesting user's perspective, so notification and outbox screens can render people without extra profile calls.

Content owners can now edit posts with `PATCH /social/content/{contentId}` to update caption and audience scope while refreshing hashtag and caption-mention graph edges. Owners can remove posts with `DELETE /social/content/{contentId}?actorUserId=...`; deletion clears attached comments, reactions, saves, shares, hides, reports, tags, mentions, activities, and the content record from both memory and Neo4j repository modes.

Hashtag discovery extracts normalized tags from content captions, returns them on content responses, and exposes `GET /social/tags/{tag}/content?viewerId=...` plus `GET /social/tags/trending?viewerId=...` with audience and hide filtering.

Users can follow topics with `PUT /social/tags/{tag}/follows`, unfollow with `DELETE /social/tags/{tag}/follows/{userId}`, list interests via `GET /social/users/{userId}/followed-tags`, and read an audience-filtered topic feed through `GET /social/users/{userId}/topic-feed`.

User follows are separate from mutual friendships: `PUT /social/users/{followedUserId}/followers`, `DELETE /social/users/{followedUserId}/followers/{followerId}`, `GET /social/users/{userId}/followers?viewerId=...`, `GET /social/users/{userId}/following?viewerId=...`, and `GET /social/users/{userId}/following-feed` support creator-style following while still enforcing blocks and content audience rules. Follow rows include lightweight `follower` and `followedUser` profile cards with display name, handle, avatar URL, visibility, and `profileVisible` so list screens and approval screens do not need per-user lookups. Public/friends-visible profiles follow immediately with `status=following`; private profiles return `status=pending` and create an incoming follow request instead of a follow edge. Pending requests are listed with `GET /social/users/{userId}/follow-requests?direction=incoming&status=pending&limit=50`, and the private-profile owner approves or rejects with `PUT /social/users/{followedUserId}/follow-requests/{followerId}/decision`. Approvals create the normal follow edge and emit activity notifications for request, accept, and reject events.

Personal mutes are available through `PUT /social/mutes`, `GET /social/users/{userId}/mutes?targetType=all&limit=50&cursor=...`, and `DELETE /social/mutes/{userId}/{targetType}/{targetId}` for `user`, `group`, and `community` targets. Blocks, mutes, and family links return named paged lists with `hasMore` and opaque `nextCursor` hints for privacy and relationship-management screens. Mutes are reversible discovery filters: they remove muted authors/circles from feed, following-feed, search, hashtag, trending-tag, and topic-feed surfaces without breaking friendships, follows, memberships, or direct content permissions.

Profile surfaces are available through `PUT /social/users/{userId}/profile` for owner-only editable metadata and `GET /social/users/{userId}/profile?viewerId=...` for a viewer-hydrated social summary. Profiles carry normalized unique handles, display names, bios, avatar URLs, website URLs, location labels, profile visibility, and timestamps; summaries also include `viewerFollowStatus` (`self`, `blocked`, `following`, `pending`, `rejected`, or `none`) plus `viewerFollowStatusUpdatedAt` so clients can render follow/request/following buttons without extra graph calls. User search hydrates from the saved profile display name/handle/bio/location instead of only hardcoded seed labels. `GET /social/users/{userId}/content?viewerId=...&limit=20` returns the user's profile timeline. The timeline reuses the same audience and hidden-content rules as feeds, so private/group/community posts only appear when the viewer can actually access them.

Circle timelines are exposed through `GET /social/groups/{groupId}/content?viewerId=...&limit=20` and `GET /social/communities/{communityId}/content?viewerId=...&limit=20`. They return only content scoped to that group/community target and still apply membership, block, and hidden-content filtering for the requesting viewer.

Public circle self-service membership is available through `GET /social/groups?viewerId=...&q=creators&visibility=public&limit=50&cursor=...`, `GET /social/communities?viewerId=...&q=city&visibility=public&limit=50&cursor=...`, `PUT /social/groups/{groupId}/join`, `DELETE /social/groups/{groupId}/leave/{userId}`, `PUT /social/communities/{communityId}/join`, and `DELETE /social/communities/{communityId}/leave/{userId}`. Group and community directories return named paged lists with `hasMore` and opaque `nextCursor` hints, while optional `q` and `visibility=all|public|private|invite_only` filters let clients browse searchable slices without local filtering. Supplying `viewerId` hydrates each row with `viewerRole`, membership, pending join-request/invite, owner-block, `canJoin`, `canRequestJoin`, and last-owner-aware `canLeave` flags for actionable directory cards. Direct join is limited to public circles, while member-management routes still handle private or invite-only circles, and leaving protects the last owner.

Private and invite-only circle growth now has an explicit request/invite workflow. Private groups and communities accept `POST /social/groups/{groupId}/join-requests` or `POST /social/communities/{communityId}/join-requests`; owners/admins list pending requests with `GET .../join-requests?actorUserId=...&status=pending` and approve or reject with `PUT .../join-requests/{requestId}/decision`. Invite-only circles reject self-service join requests and use `POST .../invites`; invited users see pending invitations through `GET /social/users/{userId}/circle-invites?status=pending` and accept or decline with `PUT .../invites/{requestId}/decision`. Users can also read their submitted join requests with `GET /social/users/{userId}/circle-join-requests?status=pending`. Accepted invitations and approved requests create normal `member` memberships, while owner/admin checks and block safeguards stay enforced.

Circle member-management routes support actor-aware permissions with optional `actorUserId` query params: `PUT /social/groups/{groupId}/members?actorUserId=...`, `PUT /social/groups/{groupId}/members/{memberId}/role?actorUserId=...`, `DELETE /social/groups/{groupId}/members/{memberId}?actorUserId=...`, and the matching community routes. Group/community member rosters and a user's joined groups/communities accept `limit` and `cursor`, returning `hasMore`, `nextCursor`, and `memberships` for large circles. Owners can add elevated roles and change roles, owners/admins can add regular members, admins can remove regular members, and last-owner protection still applies. Ownership transfer uses `PUT /social/groups/{groupId}/ownership-transfer` or `PUT /social/communities/{communityId}/ownership-transfer` with `actorUserId` and `newOwnerId`; the new owner must already be a member, the actor must be an owner, and the previous owner is demoted to admin.

Circle content moderation is available through `PUT /social/groups/{groupId}/content/{contentId}/moderation` and `PUT /social/communities/{communityId}/content/{contentId}/moderation`. Owners/admins can submit `action=remove` to hide content scoped to that circle from circle timelines, feeds, search, tag/topic feeds, profile timelines, direct reads, and content-access checks with reason `circle_moderated`; `action=restore` makes it visible again. Moderation audit trails are listed with `GET /social/groups/{groupId}/content-moderation?actorUserId=...&status=removed&limit=50` and the matching community route. Content hard deletion also clears moderation records in memory and Neo4j modes.

Viewer-aware discovery is available through `GET /social/search?viewerId=...&q=...&types=users,groups,communities,tags,content&limit=20&cursor=...`. Search ranks text matches with social context while filtering blocked users and private/hidden content, then returns `hasMore` and an opaque `nextCursor` so clients can page through people, circles, hashtags, and visible posts without losing rank order.

Graph endpoint request normalization is centralized in `SocialGraphEndpointReadModel`, keeping `/social/graph`, `/social/network`, `/social/neighborhood`, `/social/relationships/path`, and `/social/graph/repository` id/depth/limit validation, endpoint defaults, and repository-status projection out of `SocialService`.

The social graph persistence contract is split into domain ports: `SocialRelationshipGraphStore`, `SocialCircleGraphStore`, `SocialContentGraphStore`, `SocialActivityGraphStore`, `SocialMonetizationGraphStore`, and `SocialGraphMetadataStore`. `SocialGraphRepository` remains as a compatibility facade while relationship/profile and circle write/read models begin depending on the narrower ports.

Content/tag read models, engagement summaries, activity read/write flows, the activity publisher, user-interest indexing, and the ad monetization store now consume those narrower graph ports directly, reducing accidental coupling to unrelated friend/circle/content/ad persistence methods.

Neo4j driver/session concerns are centralized in `Neo4jSocialGraphClient`, keeping connectivity status, database session configuration, schema bootstrap loading, and read/write transaction helpers separate from `Neo4jSocialGraphRepository`'s social record mapping and Cypher contracts.

Neo4j record value conversion is centralized in `Neo4jRecordValues`, keeping timestamp shape normalization, nullable timestamp handling, string-list extraction, and ISO serialization reusable as Neo4j record mappers continue to split into smaller modules.

Neo4j ad campaign and event mapping is centralized in `Neo4jAdRecordMapper`, keeping monetization record hydration and Cypher parameter maps separate from the broader social graph repository. Neo4j monetization Cypher is centralized in `Neo4jAdCypher`, keeping advertiser ownership, campaign reads/writes, and ad event attribution statements out of the repository class.

Neo4j content and interaction mapping is centralized in `Neo4jContentRecordMapper`, keeping post, reaction, comment, tag, save, share, hide, report, mention, and activity record hydration reusable while the repository owns only Cypher execution and persistence routing. Neo4j content Cypher is split across `Neo4jContentCypher`, `Neo4jEngagementCypher`, `Neo4jTagCypher`, `Neo4jContentSafetyCypher`, `Neo4jMentionCypher`, and `Neo4jActivityCypher`, keeping lifecycle, engagement, discovery, safety, mention, and notification statements out of the repository class.

Neo4j relationship/profile and circle workflow mapping is split into `Neo4jRelationshipRecordMapper` and `Neo4jCircleRecordMapper`, keeping friend, follow, profile, block, mute, family, group, community, membership, join/invite, and circle-moderation rows out of `Neo4jSocialGraphRepository`.

Neo4j relationship/profile persistence is delegated to `Neo4jRelationshipGraphStore`, group/community workflow persistence is delegated to `Neo4jCircleGraphStore`, content/engagement/tag/safety/mention persistence is delegated to `Neo4jContentGraphStore`, activity persistence is delegated to `Neo4jActivityGraphStore`, and ad monetization persistence is delegated to `Neo4jMonetizationGraphStore`; all use shared `Neo4jGraphStoreSupport` read/write helpers so `Neo4jSocialGraphRepository` can keep shrinking toward a composed facade instead of owning every domain implementation.

Ad monetization endpoint orchestration is grouped in `SocialMonetizationCoordinator`, keeping campaign creation, delivery, event tracking, reporting, audience preview, social access checks, and ad limits out of the main `SocialService` constructor.

Relationship endpoint orchestration is grouped in `SocialRelationshipCoordinator`, keeping friend request, follow, close-friend, block, mute, and family-link workflows behind one relationship boundary while `SocialService` keeps its public facade methods stable.

Circle endpoint orchestration is grouped in `SocialCircleCoordinator`, keeping group, community, membership, join/invite, ownership transfer, circle content, and moderation workflows behind one circle boundary.

Content endpoint orchestration is grouped in `SocialContentCoordinator`, keeping lifecycle writes, access checks, tag/topic feeds, reactions, saves, shares, reports, mentions, and comments behind one content boundary while feed and search stay on their own service paths.

Feed endpoint orchestration is grouped in `SocialFeedCoordinator`, keeping global feed, following feed, and user timeline reads behind one feed boundary with shared ranking, visibility, engagement, and profile presentation collaborators.

Search endpoint orchestration is grouped in `SocialSearchCoordinator`, keeping user, group, community, tag, and content discovery behind one search boundary with shared scoring, visibility, relationship, mute, and pagination collaborators.

Activity endpoint orchestration is grouped in `SocialActivityCoordinator`, keeping inbox/outbox reads, unread summaries, single mark-read, and mark-all-read workflows behind one activity boundary.

Recommendation endpoint orchestration is grouped in `SocialRecommendationCoordinator`, keeping friend recommendation planning, cursor pagination, preview hydration, and recommendation limits behind one recommendation boundary.

Graph endpoint orchestration is grouped in `SocialGraphCoordinator`, keeping graph summaries, network projections, neighborhood reads, connection paths, repository status, relationship context, and visibility decisions behind one graph boundary.

Audience endpoint orchestration is grouped in `SocialAudienceCoordinator`, keeping audience previews, single and batch visibility decisions, access checks, and audience decision limits behind one audience boundary.

Profile endpoint orchestration is grouped in `SocialProfileCoordinator`, keeping profile updates, viewer-aware profile summaries, user statistics, and relationship context hydration behind one profile boundary.

Content surface collaborators are grouped in `SocialContentSurfaceSupport`, keeping shared content presentation, profile-card hydration, engagement summaries, ranking, and stable content pagination wiring out of the main service constructor.

Neo4j relationship/profile Cypher is centralized in `Neo4jRelationshipCypher`, keeping friend request, friendship, close-friend, follow, profile, block, mute, and family statements plus mute target routing out of the repository class.
Neo4j circle Cypher is centralized in `Neo4jCircleCypher`, keeping group/community directory, membership, join-request, invite, and circle-moderation statements plus circle request routing out of the repository class.

Visibility decisions are centralized in `SocialVisibilityReadModel`, keeping self/friend/close-friend/pending/blocked/public profile, interaction, friend-request, and location gates reusable for profile cards, relationship context, feeds, content access, and future monetization eligibility while `SocialService` keeps endpoint orchestration.

Relationship mutation rules are centralized in `SocialRelationshipPolicy`, keeping block checks, friend/pending-request matching, private-profile follow approval, close-friend lookup, and block-driven cleanup of friendships/follows reusable across social workflows.

Relationship response hydration is centralized in `SocialRelationshipPresentationResolver`, keeping friend, follow, block, and family DTO shaping separate from endpoint orchestration while sharing the same profile-card hydration.

Relationship list reads are centralized in `SocialRelationshipReadModel`, keeping friend request inboxes, friend and close-friend pages, follow-request queues, follower/following lists, block lists, mute lists, family links, cursor IDs, and block-safe family filtering reusable while `SocialService` keeps request validation and response hydration.

Relationship writes are centralized in `SocialRelationshipWriteModel`, keeping friend requests, close-friend edits, follows/private follow approvals, blocks, mutes, family links, relationship cleanup, and follow activity fanout reusable while endpoint write orchestration handles API response hydration.

Relationship endpoint writes are centralized in `SocialRelationshipEndpointWriteModel`, keeping friend/follow/block/mute/family write response hydration and void command delegation out of `SocialService` while `SocialRelationshipWriteModel` owns the mutation rules.

Audience preview reads are centralized in `SocialAudiencePreviewReadModel`, keeping enumerable audience candidates, block exclusion, public hidden counts, preview limits, and relationship bucket classification reusable while `SocialAudienceReadModel` handles endpoint normalization and target validation.

Audience endpoint read handling is centralized in `SocialAudienceReadModel`, keeping preview normalization, one-off decisions, batch decision de-duplication, access allow/deny buckets, and response metadata reusable behind `SocialAudienceCoordinator`. `SocialAudienceDecisionPlanner` owns public/private/friends/close-friends/family/circle visibility reasons, target validation, and circle member checks for content access, feeds, comments, search, and future monetization eligibility.

Content access batch reads are centralized in `SocialContentAccessReadModel`, keeping `/social/content/access` request validation, content lookup, de-duplicated content IDs, visible/hidden buckets, and response metadata out of `SocialService`. `SocialContentAccessResolver` owns audience decisions, circle moderation, per-user hides, and user/circle mutes across feeds, search, tag/topic discovery, profile timelines, ads, and direct content reads.

Circle membership rules are centralized in `SocialCircleMembershipPolicy`, keeping owner/admin authorization, last-owner protection, join eligibility, invite/request state, and viewer circle actions reusable for group/community workflows and future graph/monetization checks.

Circle response hydration is centralized in `SocialCirclePresentationResolver`, keeping group/community member counts, viewer action state, membership, membership request, and circle moderation DTO shaping separate from service orchestration.

Circle read data shaping is centralized in `SocialCircleReadModel`, keeping group/community directory filters, target and user membership pages, circle content pages, viewer membership flags, and circle content visibility gating reusable.

Both responses now include an aggregate `visibility` report with mode, audience source/health, fallback state, candidate counts, hidden counts, and hidden reason buckets, giving clients privacy-safe explainability without exposing hidden users. `PresenceSpatialReadModel` now owns nearby/minimap normalization, candidate filtering, and response assembly; it goes through `PresenceRepository.findActiveWithinRadius`, batches candidate owners through a `PresenceAudienceAccessClient`, and then applies `PresenceVisibilityPolicy` decisions for viewer exclusion, social/public visibility, and owner share-radius bounds. The default local audience client preserves current public-only behavior; set `jezaku.presence.audience-access.source=http` plus `jezaku.presence.audience-access.social-base-url=http://localhost:8103` to evaluate candidate owners through social `/social/audience/access`, with `fallback-to-local=true` keeping presence available when social is offline. `GET /presence/ops/health` reports active/stale presence counts plus audience-access requested/effective source, readiness, fallback state, config issues, and recommended actions for ops dashboards. `PresenceSpatialProjection` centralizes distance, bearing, relative X/Y, altitude delta, and freshness mapping for both nearby lists and minimap dots. That keeps the current in-memory backend behavior stable and gives the future Postgres/PostGIS, Redis GEO, or social-visibility adapter implementation a clean query boundary.

The context response includes a top-level `summary` object with `layerCount`, `readyLayerCount`, `totalAvailableDots`, `truncatedLayerCount`, `perimeterCount`, `liveCount`, `freshCount`, `staticCount`, `arReadyMemoryCount`, `lowConfidenceMemoryCount`, `needsRefinementMemoryCount`, `criticalAdvisoryCount`, `warningAdvisoryCount`, `infoAdvisoryCount`, `blockingAdvisoryCount`, `highestAdvisoryPriority`, `nearestDistanceMeters`, and `farthestDistanceMeters`. Each layer also includes a `summary` object for collapsed minimap UI: `nearestDistanceMeters`, `farthestDistanceMeters`, `perimeterCount`, `liveCount`, `freshCount`, `staticCount`, and the same memory anchor confidence rollups summarize the returned dots without requiring the client to scan the whole dot array.

The response also includes a nullable `focus` object. Safety advisories win focus by priority, so blocking zones can drive HUD banners immediately; when no advisory is active, focus falls back to the nearest returned dot. People focus targets keep `displayMode=marker`, while AR-ready memory focus targets use `displayMode=ar_photo` and include the same `anchor` object carried by memory dots and minimap pins, including structured `confidence` score/reason/action details for capture-refinement UI. Dot-backed focus objects include `href`, `distanceMeters`, `bearingDegrees`, `relativeBearingDegrees`, `relativeX`, `relativeY`, and `altitudeDeltaMeters`, so the camera UI can draw reticles and arrows without looking the dot up again.

The `refresh` object gives client polling guidance with `recommendedPollSeconds`, `maxAgeSeconds`, `nextExpiringDotSeconds`, and a `reason` such as `blocking_advisory`, `warning_advisory`, `live_activity`, `ambient`, or `idle`. Blocking safety contexts refresh fastest, live camera activity refreshes at a medium cadence, and ambient seeded contexts can poll more slowly.

The `minimap` object describes the heading-up radar viewport used by the camera UI. It includes the center point, radius, orientation, north indicator coordinates, three distance rings, returned versus total-available dot counts, perimeter count, and a truncation flag so compact/minimized minimap states can avoid scanning every layer. It also includes flattened `pins` sorted by render priority, carrying display mode, thumbnail, AR anchor readiness, anchor confidence, relative x/y, distance, perimeter flag, and first action href for direct minimap drawing. Memory pins use `displayMode=ar_photo` only when the anchor is AR-ready and `publicMemoryEligible=true`; low-confidence or media-ineligible memories remain softer `photo_hint` discovery markers. `clusters` groups nearby pins for compact radar rendering while leaving the individual pins available for expanded mode. `layerControls` lists the returned minimap layers with labels, display modes, status, counts, truncation state, and default toggle metadata for minimized/full minimap controls. `badges` summarizes safety alerts, live people, people, AR-ready memories, anchor-refinement needs, memories, hidden dots, and perimeter dots for collapsed minimap indicators.

Every minimap dot includes `source`, `visibility`, `expiresAt`, `ageSeconds`, `expiresInSeconds`, `distanceBucket`, and `freshnessState` metadata. People dots use `source=live_session` for active camera sessions, `source=presence_service` for service-backed nearby users, and `source=seed` for seeded presence, with `expiresAt`, `expiresInSeconds`, and freshness hints available for client-side fading. `distanceBucket` is one of `near`, `mid`, `far`, or `perimeter`, and `freshnessState` is one of `fresh`, `recent`, `stale`, `expired`, or `static`. Memory dots also include `mediaId`, media status, moderation status, memory attachment eligibility, public-memory eligibility, and an `anchor` object with `type`, `quality`, `arReady`, position, heading, compass, pitch/roll, GPS accuracy, and `confidence`, matching the memory and media service capture contracts. When anchor confidence recommends refinement, the memory dot exposes a `review_anchor` action targeting `/memories/{memoryId}/anchor`, and the matching HUD advisory reuses that action. Flattened minimap pins carry the memory `mediaId` and `publicMemoryEligible` flag as well, so minimized camera UI can hydrate thumbnails/photos without scanning the full layer payload. Safety dots use the same base contract with stable seed metadata and `expiresInSeconds=null` so the Flutter minimap can render mixed layers without type-specific shape checks.

The camera service also owns live camera sessions: `POST /camera/sessions` creates a short-lived session with viewer telemetry, `PATCH /camera/sessions/{sessionId}` refreshes the live position/heading/status, `POST /camera/sessions/{sessionId}/heartbeat` cheaply extends the live TTL between sensor updates, `POST /camera/sessions/{sessionId}/pause` temporarily removes a backgrounded camera from active HUD/minimap projection while preserving resumable state, `POST /camera/sessions/{sessionId}/resume` returns it to the live set with a refreshed TTL, `POST /camera/sessions/{sessionId}/end` explicitly closes the camera lifecycle when the screen exits, and `GET /camera/sessions/{sessionId}` reads it back. Public and trusted friends-only active sessions are projected into the `people` layer, while private sessions and blocked viewers stay out of nearby minimap results. `CameraVisibilityService` currently mirrors seed friend/block rules and is the handoff point for the social service visibility adapter. `GET /camera/sessions/{sessionId}/minimap?layers=people,memories&radiusMeters=100` reuses the active session telemetry and returns the same standalone minimap shape for minimized live-camera UI, while `GET /camera/sessions/{sessionId}/context?layers=people,memories&radiusMeters=100` remains available when clients need the full HUD context. `GET /camera/sessions/{sessionId}/sync?layers=people,memories&radiusMeters=100&eventLimit=50&afterSequence=0&contextDeltaLimit=50` bundles the current session, HUD/minimap context, cursor-based session event timeline, a context-level `contextDelta` block, an embedded `opsHealth` source-health report for the same context slice, a `syncPlan`, a flattened `freshness` summary, follow-up `links`, a compact `capabilitiesRef`, the full `capabilities` contract by default, and a `stream` descriptor containing the SSE `href`, `contentType`, `afterSequence`, `maxEvents`, and `retryMillis` for the next realtime connection. Clients that already cached `/camera/capabilities` can pass `capabilitiesMode=etag&capabilitiesEtag=...` to omit the heavy `capabilities` object; the response keeps `capabilitiesRef` with the current contract ETag, `clientCacheFresh`, and `refreshRecommended`, and `links.nextSyncHref` preserves the thin-mode knobs for follow-up syncs. Clients can also pass `sections=clientHints,freshness,links` using comma-separated names from `supportedSyncResponseSections`; the default is `all`, unsupported names return `400`, unselected top-level fields are omitted from JSON, derived work such as `contextDelta` and `opsHealth` is skipped when no selected section depends on it, and `links.nextSyncHref` preserves the canonical section subset for follow-up syncs. `clientHints` translates the same state into reducer-friendly guidance: whether to refresh capabilities, whether cached capabilities can be used, the preferred next transport (`sse` or `sync`), preferred next href, stream/sync hrefs, event-stream and polling booleans, offline-safety for cached rendering, and machine-readable reasons such as `capabilities_included`, `capabilities_cache_fresh`, `event_stream_available`, `sync_backlog`, or `ops_health_attention`. `freshness` mirrors the active sync plan as client-friendly timing metadata with `generatedAt`, refresh-after seconds/time, max-age seconds, stale time, immediate-refresh and stale booleans, and the scheduling reason. `contextDelta` compares the latest filtered HUD context with the previous sync for the same session and emits lightweight `dot.entered`, `dot.left`, `dot.updated`, `advisory.active`, `advisory.cleared`, and `layer.health.changed` events for camera UI transitions without mixing them into the lifecycle SSE stream. Dot updates fire only for stable semantic changes such as distance bucket, freshness, display mode, anchor confidence/readiness, public-memory eligibility, or media/moderation state changes, while layer health changes fire when layer status, source selection, source health, fallback state, fallback reason, or truncation changes. Delta events include `changeReasons`, current `distanceBucket`, `freshnessState`, `anchorConfidenceLevel`, `anchorArReady`, and `previousDistanceMeters`, while the response rolls up `dotUpdatedCount` and `layerEventCount` beside enter/left/advisory counts. `contextDeltaLimit` bounds the returned delta list to 1-100 events; `count` is the returned event count, `totalAvailableCount` is the pre-limit count, and `truncated=true` tells clients to rely on the full `context` payload for the remaining transitions. `syncPlan` summarizes the next client cadence with `recommendedSyncAfterSeconds`, `nextSyncAt`, `maxContextAgeSeconds`, `contextStaleAt`, heartbeat and position-update seconds plus due timestamps, `eventBacklog`, `deltaBacklog`, and a reason; event or delta backlog asks for a one-second follow-up, critical `opsHealth` asks for a two-second refresh, degraded `opsHealth` asks for a five-second refresh, and otherwise the context refresh policy drives the cadence. Server-derived timestamps let clients schedule around sleep/resume and skewed device clocks without doing their own clock math. `links` carries `nextSyncHref`, `contextHref`, `eventsHref`, and `streamHref`, preserving the current layer/radius/limit knobs while advancing event cursors to the latest returned sequence. It includes `baselineKey`, `baselineReset`, and `resetReason` (`first_sync` or `view_changed`) so clients can distinguish real nearby changes from a changed layer/radius view. Pausing, ending, or updating a session into an inactive state clears the saved context baseline, so resumed sessions report a fresh first-sync delta instead of replaying stale state. `GET /camera/sessions/{sessionId}/events?limit=50&afterSequence=0` returns a chronological session event timeline with creation, heartbeat, telemetry, visibility, pause, resume, and status-change events. `GET /camera/sessions/{sessionId}/stream?afterSequence=0&maxEvents=50` exposes the same session events as `text/event-stream`, replaying cursor events first and then emitting live in-memory events until `maxEvents` is reached. Responses include `lastSequence` and `hasMore`, so clients can poll incrementally by passing the last seen sequence while keeping the same shape for a later SSE stream.

Session sync orchestration lives behind `CameraSessionSyncService`, while `CameraSessionSyncRequest` carries the query knobs across resource, service, and link-builder boundaries without repeating long argument lists. Its `fromRaw` factory normalizes `eventLimit`, `afterSequence`, and `contextDeltaLimit` once at the sync boundary, so event reads, stream descriptors, deltas, and follow-up links all use the same validated values. `CameraSessionContextQueries` owns the reusable session-to-context mapping used by both `/sessions/{sessionId}/context` and `/sessions/{sessionId}/sync`. `CameraSessionSyncCapabilityNegotiation` owns full/etag mode normalization, cache freshness checks, and section-aware embedding of the full capabilities body. `CameraSessionSyncAssembler` owns assembly of stream descriptors, optional context deltas, ops health, links, sync plans, client hints, freshness, and final projection, while `CameraSessionSyncService` stays focused on loading the active session, current context, and event cursor slice. `CameraSessionSyncWorkPlan` centralizes which selected sections require secondary derived work, and `CameraSessionSyncResponseProjector` owns the final top-level field projection so `sections=` behavior stays locally testable as the response grows. `CameraSessionSyncLinksBuilder` owns follow-up URLs, stream descriptors, canonical section query preservation, thin-capability query preservation, and the diagnostic `opsHealthHref`, keeping route construction reusable and locally testable. `CameraResource` stays focused on HTTP routing and session lifecycle cleanup instead of assembling sync plans, links, capability references, and response projection inline. Session sync `links.opsHealthHref` is a directly callable `/camera/ops/health` URL built from the session telemetry plus the active layer/radius/limit view, so clients can open the matching source-health diagnostic without rebuilding query parameters. Sync links also include `capabilitiesHref=/camera/capabilities`, giving clients a canonical route for refreshing the cached capability contract with ETag revalidation.

Session sync links also include `minimapHref`, which points at the matching `/camera/sessions/{sessionId}/minimap` route with the active radius, layer limit, and layer filter preserved for collapsed HUD refreshes.

`GET /camera/capabilities` returns the same capability contract exposed inside session sync, with `contractVersion`, supported layer names, minimap projection modes, session event types, context-delta event types, telemetry quality hints, supported link keys including `minimapHref`, supported sync capability modes (`full` and `etag`), supported top-level sync response sections such as `clientHints`, `freshness`, and `capabilitiesRef`, a `defaults` block for radius/layer limit/event cursors, default capabilities mode, and default sync response sections, a `limits` block for max radius and min/max layer/event/stream/delta bounds, reason catalogs for refresh, sync-plan, and session-guidance states, a `cache` block with the reusable cache key, contract ETag, max-age, stale-while-revalidate window, and `If-None-Match` revalidation hint, a `vocabularies` block for UI-facing dot display modes, advisory severities/display modes, minimap badge types, focus kinds, target types, distance/freshness buckets, source names, visibility scopes, health/status values, telemetry quality states, action types, action prefixes, context-delta change reasons, client-hint transports, and client-hint reasons, the SSE retry hint, and booleans for `contextDelta`, `opsHealth`, `eventStream`, `syncPlan`, and `freshness`, letting mobile clients adapt to backend contract growth before starting a live camera session. The standalone capabilities route also sends matching `ETag` and `Cache-Control` headers and returns `304 Not Modified` when the client revalidates with the current ETag.

Every camera session response includes `guidance` with `expiresInSeconds`, `telemetryAgeSeconds`, `heartbeatAfterSeconds`, `positionUpdateAfterSeconds`, control booleans, and a `reason` such as `live_active`, `paused`, `expired`, or `ended`. Live sessions advertise heartbeat and sensor-update cadence, paused sessions advertise resume/end controls, and ended sessions return no active controls.

## Client Integration

Local CORS is enabled for all services and supports `GET`, `POST`, `PUT`, `DELETE`, and `OPTIONS`.

Clients may send an `X-Request-Id` header. Each service echoes it in the response. When the client does not provide one, the service generates one.

## Error Contract

All services return the same JSON shape for request errors:

```json
{
  "code": "BAD_REQUEST",
  "message": "lat and lng query parameters are required",
  "status": 400,
  "path": "/memories/nearby",
  "requestId": "camera-1717040000",
  "timestamp": "2026-05-30T00:00:00Z"
}
```

Common codes include `BAD_REQUEST`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `UNSUPPORTED_MEDIA_TYPE`, and `INTERNAL_ERROR`.

## Reactive Dispatch

Resource classes that wrap synchronous in-memory work in `Uni` should use blocking dispatch so validation, map updates, stream sorting, and JSON serialization run on worker threads instead of the Vert.x event loop. This keeps the current prototype stores safe while the services are still moving toward reactive persistence.
